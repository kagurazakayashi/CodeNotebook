## 已确认的拦截事件

卡巴斯基在这台机器上实际造成过两类不同的故障，症状和位置完全不同，排查时必须先区分：

| 案别 | 触发组件        | 症状                         | 处理方向                   |
| ---- | --------------- | ---------------------------- | -------------------------- |
| 案一 | 加密连接扫描    | DSH 模型请求频繁重试         | 让 Node 信任卡巴斯基根证书 |
| 案二 | 系统监控（PDM） | 组件文件被删除、命令偶发中断 | 受信任应用程序 + 恢复文件  |

### 案一：加密连接扫描导致 DSH 模型频繁重试

症状：模型调用频繁重试，报 `DeepSeek Messages transport failed`。

根因：卡巴斯基的加密连接扫描对 HTTPS 做中间人替换。Node 使用自带的 CA 列表，不认识卡巴斯基的根证书，于是 TLS 校验失败。

实测数据（2026-10-06）：

| 观察视角                          | api.deepseek.com                                        | 说明                               |
| --------------------------------- | ------------------------------------------------------- | ---------------------------------- |
| .NET / Windows 信任存储           | 签发者为 Kaspersky Anti-Virus Personal Root Certificate | 三个域名全部被替换，确认存在中间人 |
| Node 默认信任（裸 TLS，12 次）    | 8 次失败 SELF_SIGNED_CERT_IN_CHAIN                      | 失败率约 67%                       |
| Node 默认信任（真实 fetch，8 次） | 2 次失败                                                | 走 127.0.0.1:23333 代理的真实路径  |
| Node 加卡巴斯基根证书             | 12/12 与 12/12 全部通过                                 | 其中 5/12 仍显示 Kaspersky 签发    |

拦截是间歇性的：同一域名的签发者在 TrustAsia（真实证书）与 Kaspersky 之间随机切换，所以表现为偶发重试而不是持续失败。被拦截的域名包括 `api.deepseek.com`、`platform.deepseek.com`、`dsh-otel-collector.deepseeksvc.com`。

三种方案的取舍：

| 方案                                                 | 可实施性                | 代价                                                                   |
| ---------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------- |
| 卡巴斯基排除域名                                     | 可实施                  | 仅为枚举到的域名放弃 HTTPS 内容扫描，需自行维护列表                    |
| 关闭 Node 证书校验（NODE_TLS_REJECT_UNAUTHORIZED=0） | 可实施，但不能写进 .env | 进程内所有 HTTPS 都不再校验，含 web_fetch、插件安装、MCP、遥测、云同步 |
| NODE_EXTRA_CA_CERTS 指向卡巴斯基根证书（已采用）     | 可实施，同样不能用 .env | 只多信任一个本地杀软根证书，校验保持开启                               |

已采用的做法：

1. 导出卡巴斯基根证书到 `C:\Users\yashi\.dsh\certs\kaspersky-root-ca.pem`，SHA-1 指纹 `957B463C3C25EAB9A30A8730F0E9A80008D41BE8`，有效期至 2036-02-16。
2. 设置用户级环境变量 `NODE_EXTRA_CA_CERTS` 指向该文件。
3. 验证：裸 TLS 12/12 通过、真实 fetch 12/12 通过，且 5/12 仍显示卡巴斯基签发，说明内容扫描没有被削弱。

需要注意的四个坑：

1. 绝不能写进 `.env`。DSH 的 `dsh-app-boot` 在 `readEnvLayer` 里逐个检查 `.env` 的键，命中 `NODE_EXTRA_CA_CERTS`、`NODE_TLS_REJECT_UNAUTHORIZED`、`SSL_CERT_FILE`、`SSL_CERT_DIR`、`CURL_CA_BUNDLE`、`REQUESTS_CA_BUNDLE` 等引导变量就直接抛错，进程起不来。代理类变量是唯一例外，且只允许放在 `~/.dsh/.env`。
2. 该变量只在 Node 启动时读取，改完必须重启终端与 dsh。
3. 用户级变量对全部 Node 工具生效（opencode、Qoder CLI、petdex 等），不只是 DSH。
4. 卡巴斯基轮换根证书后 PEM 会失配，需重新导出。

### 案二：行为检测删除了 dsh-subprocess-local/lib/runner.js

卡巴斯基报告原文要点：

| 字段        | 值                                                                     |
| ----------- | ---------------------------------------------------------------------- |
| 事件        | 进程已终止                                                             |
| 应用程序    | Node.js JavaScript Runtime                                             |
| 组件        | 系统监控                                                               |
| 类型 / 名称 | 木马 / PDM:Trojan.Win32.Generic                                        |
| 威胁级别    | 高                                                                     |
| 对象        | 进程，路径 `...\@deepseek-ai\dsh-subprocess-local\lib`，名称 runner.js |
| MD5         | 5291FC959AE92F10816EBAED06AC813F                                       |

`PDM:` 前缀表示这是主动防御（System Watcher）的纯行为启发式判定，没有任何特征码命中。

核实证据链：

| 核实项                            | 结果                                                        |
| --------------------------------- | ----------------------------------------------------------- |
| 官方 npm 包是否包含 lib/runner.js | 包含，13483 字节                                            |
| 官方文件 MD5 对比报告 MD5         | 完全一致，说明是正品文件，属误报                            |
| 磁盘上该文件是否存在              | 不存在（Test-Path、cmd dir、Get-Item 三种方式一致）         |
| 同目录其他文件                    | index.js、output.js、runner-launch-B2zsQ1Dz.js 均完好       |
| lib 目录的修改时间                | 17:35，而幸存文件都是 12:38，说明是后来被删除，不是从未安装 |
| 同结构的对照包                    | dsh-sandbox-windows-acl\lib\runner.js 完好，排除打包问题    |

为什么一个沙箱组件会被判成木马：`dsh-subprocess-local` 依赖 `koffi`（直接 FFI 调用 Win32）与 `node-pty`（分配伪控制台），而 `dsh-sandbox-windows-acl` 的 runner 会创建 WRITE_RESTRICTED 受限令牌、改写目录 ACL（授予与回收 capability SID）、派生进程、退出时回收权限。一个进程同时做「加载 FFI、调用 Win32 创建受限令牌、重写文件系统 ACL、派生进程」，在行为引擎眼里与提权类木马几乎无法区分。因此这是可理解的行为误报，不是随机误杀。

修复顺序（顺序不能反）：

1. 先加排除项，否则恢复后会被再次删除。
2. 再恢复文件：优先从卡巴斯基隔离区还原原件，或用 `npm install -g @deepseek-ai/dsh@0.2.0-rc.2` 重装整棵树。
3. 最后验证文件存在、MD5 正确、命令可执行。

当前状态：已恢复（2026-10-06 17:42），MD5 与官方一致，文件时间戳为 npm 包归一化的 1985-10-26，说明是由 npm 包恢复而非隔离区还原，字节与发布版本一致。

## 复发时的排查顺序

1. 先看卡巴斯基报告：更多工具 > 报告 > 检测历史。按组件名区分类型——文件反病毒、系统监控（PDM）、加密连接扫描，三者的处理方式完全不同。
2. 若是系统监控（PDM），检查组件完整性：`Test-Path "D:\npm\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai\dsh-subprocess-local\lib\runner.js"`，并用 Get-FileHash 核对 MD5 是否为 5291FC959AE92F10816EBAED06AC813F。
3. 白名单永远取最小粒度：优先用检测记录自带的「添加到排除项」生成针对该对象的规则，其次才是受信任应用程序，且只勾必要权限。
4. 记住白名单不会还原被删除的文件：加完排除项后必须再恢复文件并验证。
5. 仍失败才逐条加条件加项，一次只加一条，避免滑向过度排除。
